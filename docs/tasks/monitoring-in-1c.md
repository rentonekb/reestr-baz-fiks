# Мониторинг целиком в 1С (решение пользователя 21.10.2026)

Всё — регламентными заданиями расширения РеестрБазФикс в base_list, без Windows-планировщика и агента rbf_agent.
Задачи RBF-Agent-Metrics / RBF-Agent-Techlog на 88.90 удаляются после того, как этапы А и Б заработают (с «да» пользователя).
Настройки — только в форме «Настройки мониторинга» (страницы «Агенты» → переименовать в «Серверы», «Регламентные задания»).
Контракт событий и регистр рбфВыполненияТЖ — `docs/tj-events-schema.md`; запись событий — `рбфАнализСервер.ПринятьВыполненияТЖ`
(принимает массив Соответствий в формате JSON tj-events — использовать его, а не писать вторую запись).

## Этап А. Сбор ТЖ (регл. задание рбфСборТЖ, раз в минуту)
- Сервер base_list (rphost на S2019, учётка службы service.1c.AL) читает файлы ТЖ сам: для S2019 — локальный каталог
  (КаталогТЖ сервера, по умолчанию D:\logs_1c\rbf), для других серверов — UNC-путь из настроек сервера.
- Дочитывание с позиции: регистр рбфПозицииФайловТЖ (Сервер, Путь → Смещение байт, Изменено). Файлы *.log с именем yyMMddHH,
  изменённые за 2 ч. В файле текущего часа последнее событие не брать (может быть недописано). Первый запуск по серверу — встать в конец.
  BOM в начале файла. Чтение с разделением доступа (файл пишет платформа) — проверить ФайловыйПоток / ФайловыеПотоки.
- Разбор — `рбфАнализСервер.СвойстваСобытияТЖ`; события DBMSSQL, SDBL, CALL, TLOCK, TTIMEOUT, TDEADLOCK, EXCP, QERR;
  пропуск EXCPCNTX и CALL IVResourceRemoteConnection.send; ключ/Ид и дедупликация копий из разных логов — как в агенте
  (`C:\claude\knowledge\baselist\agent\rbf_agent.ps1`, функции Send-OnlineEvents, New-TjEvent: сервер|каталог rphost|файл|мм:сс.дробь|длительность|событие|t:connectID).
- Лимит за запуск (например 20000 событий / 50 с), остальное — в следующий запуск.
- Почасовые агрегаты рбфСобытияТЖ: регл. задание рбфАгрегатыТЖ раз в час (в :05) считает закрытый час из рбфВыполненияТЖ
  и пишет через существующую ПравилаРеестраБаз.ПринятьСобытияТЖ (те же ключи, что у агента: Event-Key в агенте), тревоги как сейчас.
## Этап Б. Счётчики (регл. задание рбфСчетчикиСерверов, раз в 5 минут)
- Порт Get-Metrics / Get-SqlMetrics агента: CPU, память, диски, процессы rphost/ragent/rmngr/sqlservr через COM WMI
  (WbemScripting.SWbemLocator, для удалённого сервера — по имени), SQL — sys.dm_os_performance_counters тем же способом, что
  уже используется в расширении для запросов к SQL (найти КомандаSQL / ADO). Запись — как метод metrics (ПравилаРеестраБаз).
## Этап В. Анализ (регл. задание рбфАнализСобытийТЖ, раз в минуту)
1. Снимок «держит сейчас»: сеансы кластеров (rac session list, как в ПравилаРеестраБаз для кластеров) с blocked-by-ls / blocked-by-dbms
   и SQL-цепочка (sys.dm_exec_requests blocking_session_id, wait_time, текст) → регистр рбфБлокировкиСейчас (снимок, перезаписывается).
2. Инциденты блокировок: TLOCK/TTIMEOUT дольше порога (ПорогОжиданияБлокировкиСекунд, по умолчанию 5), все TTIMEOUT и TDEADLOCK
   за прошедшую минуту, группировка по виновнику (ВиновникИд → пользователь, контекст, запрос) → регистр рбфИнцидентыТЖ
   (Время, Вид, Сервер, База, Пространство, Жертв, ОжиданиеСек, Виновник*, Пример Ид, Отправлено).
3. Долгие запросы: шаблоны (ШаблонХеш), у которых средняя длительность за последний час выросла к 7-дневной более чем в N раз
   (настройка) при не менее M выполнений → инцидент «деградация запроса».
4. Telegram: инциденты выше порога — сообщение с виновником (ПравилаРеестраБаз.ОтправитьТелеграм), не чаще раза в N минут
   на одного виновника/шаблон.
5. Форма «Блокировки»: страница «Сейчас» (снимок + последние инциденты, автообновление раз в минуту), «Инциденты».
## Сверка с методикой ИТС (22.10.2026)
Источники: its.1c.ru/db/content/metod8dev/src/developers/scalability/troubleshooting/i8106006.htm (ожидания на блокировках),
.../scalability/methods/i8105809.htm (мониторинг на продуктивных серверах, highload), i8105808, i8105861, i8105900, i8105814/15, i8106008.
Тексты статей: scratchpad сессии 22.10 (its\*.txt) - при необходимости скачать заново (windows-1251).
Сделано: TLOCK снова пишутся все (TLOCK виновника - с пустым WaitConnections, по ИТС его нельзя отсекать порогом/фильтром).
План (по порядку):
1. Виновник управляемой блокировки по ИТС: соединение из WaitConnections -> его TLOCK в пределах его транзакции
   (окно от начала транзакции; начало = Время Commit/Rollback минус длительность SDBL Commit) по тому же пространству
   и пересечению значений полей Locks; в карточке - длительность транзакции виновника и что в ней выполнялось.
2. Регистр: TLOCK без ожидания, на которые не сослалось ни одно ожидание, удалять через 15 мин (рег. задание очистки).
   Форма «Блокировки» по умолчанию - только события с ожиданием.
3. Логи раздельные со своим history: 1C_Locks history 4 ч (ИТС), остальные по настройке.
4. Блокировки СУБД: события DBMSSQL с lka=1 / lkp=1 (сервис вспомогательных функций кластера) + свойства lka,lkp,lkpid,lkaid,
   lksrc,lkpto,lkato; виновник по lksrc (соединение 1С), сопоставление spid<->dbpid и XE - запасные.
5. Журнал длинных событий: все события с Durationus >= 20 с (history 28) - видно длинные EXCP/CALL/SCALL и Commit.
6. Минимальный прод-журнал: EXCP, CONN, PROC, ADMIN, SESN, CLSTR + <dump type="3"> - падения rphost, перезапуски.
7. Пороги в logcfg перевести на Durationus (мкс) - без двусмысленности единиц Duration.
8. Контроль ТЖ: размер/рост каталогов в час; через минуту после смены logcfg проверять, что журнал пишется
   (ошибка или посторонний файл молча выключают запись); суточный архив ТЖ со сжатием.
9. Этап В «держит сейчас»: rac session list (blocked-by-ls/dbms, время вызова текущее, память текущая) +
   sys.dm_tran_session_transactions/dm_exec_requests (длительные транзакции, tempdb).
10. SQL: топ запросов кэша (dm_exec_query_stats) по CPU/частоте, ожидания sys.dm_os_wait_stats (доля signal wait).
11. Позже: APDEX ключевых операций (БСП «Оценка производительности»), счётчики CPU/памяти/очереди диска (этап Б),
    оповещения о резком падении числа сеансов / подходе к лимиту лицензий.
12. plansql - только по требованию для одного шаблона на ограниченное время.
Проверено по справке 8.3.27 (Руководство администратора, Приложение 3, logcfg.xml, its.1c.ru/db/v8327doc/bookmark/adm/TI000000365):
- Duration - сотни микросекунд (наш порог 10000 = 1 с верен), Durationus - микросекунды.
- WaitConnections - соединения, с которыми идёт столкновение (TLOCK и TTIMEOUT); Regions/Locks - пространства и блокировки TLOCK.
- SDBL Func: beginTransaction пишется в момент начала и без длительности; commitTransaction/rollbackTransaction - фиксация/отмена.
- dbmslocks: не чаще 1 раза в 2 с запрос пар (жертва, источник) по соединениям СУБД; lk-свойства добавляются к ОЧЕРЕДНОМУ
  завершённому событию потока: у жертвы - один раз, у источника - до закрытия/отката транзакции (видны, в т.ч. на SDBL Commit).
  lka/lkp - источник/жертва, lkpid/lkaid - номера запросов, lksrc - номер соединения источника, lkpto/lkato - секунды.
  Значит, ловить их надо не только у DML: событие жертвы/источника может быть любым из собираемых (Commit, DBMSSQL, SDBL).
- Атрибуты <log> (новое): compress="zip" (сжатие устаревших файлов при ротации - встроенный архив ТЖ),
  format="json" (журнал объектами JSON - надёжнее нашего текстового разбора), placement="plain" (без подкаталогов
  процессов - меньше каталогов на обход; сейчас ~5000 файлов за запуск), rotation="size"/rotationsize (МБ, по умолч. 100),
  rotationperiod (ч, по умолч. 1), history=0 - не удалять. location у <log>, <dump>, <defaultlog> - разные каталоги.
- При любой ошибке БД пишется EXCP (если проходит фильтры logcfg). Дампы - элемент <dump>.
- Элемент <plansql> - планы в свойстве planSQLText событий СУБД; один на файл (глобально) - только по требованию.
Решения к плану: п.3 - разные <log> с history, 1C_Locks 4 ч, compress="zip"; рассмотреть format="json" и placement="plain"
(переписать разбор под JSON - отдельная задача, снимет ошибки разбора и ускорит); п.4 - собирать события с lka/lkp
любого типа (eq property lka/lkp value 1) в логе SQL_Locks.
Также: производительность сбора (запуск ~4 мин: запись по одной транзакции на строку, ~5000 файлов за запуск).
