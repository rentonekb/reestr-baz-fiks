# Анализ производительности, триггеры и ИИ-анализ ТЖ в base_list

## Зачем
В контуре AL нет 1С-Монитора: у myway на MSK-1C8-MON01 он есть, у нас нет. Нужно своё:
раздел «Анализ», триггеры с уведомлениями и ИИ-разбор ТЖ прямо из base_list.
Код Монитора закрыт, его не копируем. Берём только идеи (что он показывает и какие у него триггеры) и делаем лучше.

Объединяем это с облачным проектом **tj-analyzer** (rentonekb/tj-analyzer, Python CLI, этапы 1–6 готовы, этап 7 в работе).
Разбор ТЖ base_list сам не пишет, этим занимается tj-analyzer, а base_list хранит, показывает и вызывает его.

## Охват
- Серверы контура AL: 88.90 (S2019) и всё, что есть в реестре. **myway пока не добавляем.**
- Источники: ТЖ (каталоги на серверах), агенты rbf (счётчики Windows и SQL уже идут в `рбфСчетчики`),
  RAS-снимки сеансов (новое), DMV SQL раз в сутки (новое).

## Что делаем

### 1. Раздел «Анализ» (по образцу Монитора, но своё)
| Вкладка | Источник | У Монитора | Лучше чем у Монитора |
|---|---|---|---|
| График | рбфСчетчики, агрегаты ТЖ, RAS | есть | на одном графике счётчики ОС и события ТЖ, клик → расшифровка |
| Запросы | ТЖ DBMSSQL/SDBL → tj-analyzer queries | есть | нормализация текста, группировка по шаблону |
| Блокировки и взаимоблокировки | TLOCK/TTIMEOUT/TDEADLOCK → tj-analyzer locks | есть | кто кого ждал, обе стороны с контекстом |
| Ошибки ТЖ | EXCP/PROC → tj-analyzer errors | есть | группы и «мусорные» фильтры в справочнике |
| Серверные вызовы | CALL/SCALL | есть | CPU/память по контекстам |
| Сеансы (RAS) | rac session list раз в минуту | доработка myway | история по сеансу, кто держал блокировку |
| СУБД | DMV раз в сутки | есть | дополняет реестр: модель восстановления, MAXDOP, RCSI, задержки файлов, недостающие индексы |
| Ключевые операции (APDEX) | БСП ОценкаПроизводительности баз | есть | второй этап |
| Дампы | каталог дампов rphost | есть | второй этап |

### 2. Триггеры
Справочник `рбфТриггеры` (условие + порог + период + антиспам + канал TG). Регламентное задание проверяет данные.
Стартовый набор взят из списка Монитора: запрос > 1 мин, > 2 дедлоков/ч, > 4 таймаутов/ч, CPU > 75 % 1 мин,
rphost > 10 ГБ, сумма rphost > 20 ГБ, сеанс > 15 ч, диск C: < 10 ГБ, агент не прислал данные, открыт Конфигуратор,
ошибки лицензирования, найден дамп, фоновых > 50, резкое падение числа сеансов на 50 %.
Своё сверх Монитора: проверка условий на стороне 1С (без произвольного кода-«алгоритмов»), кнопка
«Разобрать ИИ» на сработке.

### 3. ИИ-анализ ТЖ
В разделе ТЖ форма «Анализ ТЖ»: каталог (UNC), период, база, кнопка «Анализировать».
- base_list пишет задание в регистр `рбфЗаданияАнализаТЖ` (статус «В очереди»).
- **Исполнитель на 88.44** (станция claude; на 88.90 нет VPN и Claude CLI) по расписанию раз в минуту
  забирает задание через HTTP-сервис base_list, запускает
  `tj-analyzer summary --json --from --to <UNC>` (читает потоково, на C: ничего не копирует),
  затем `tj-analyzer diagnose --backend claude-cli`, и возвращает JSON-агрегаты и диагноз.
- В модель уходят **только агрегаты и контексты** с обезличиванием из этапа 7 (без значений параметров
  запросов и без имён пользователей). Есть «пробный прогон»: показывает, что уйдёт в модель, без отправки.
- Диагноз хранится в base_list: проблемы (важность, заголовок, доказательства, причина, исправление, как проверить).

## Не делаем
myway, свой парсер ТЖ на BSL, копирование кода и форм Монитора, API-ключ Anthropic (только подписка CLI).
