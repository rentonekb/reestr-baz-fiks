## 1. Методика расследования производительности

### 1.1. Порядок работ: сначала APDEX, потом ТЖ
- Оптимизация по ИТС начинается с интегральной оценки по APDEX: список ключевых операций, целевое время T для каждой,
  замеры реальных пользователей. Плохие операции («Неприемлемо», «Очень плохо», «Плохо») разбираются по приоритету.
  Источники: `…/methods/i8105807.htm` (оценка по APDEX), `…/methods/i8105808.htm` (общая схема оптимизации).
- Первый шаг по выбранной операции — сырые замеры (регистр ЗамерыВремени подсистемы БСП «Оценка производительности»),
  не меньше ~100 замеров, гистограмма по секундам. Два пика на гистограмме — признак неверно встроенного замера,
  а не проблемы системы (`i8105808`).
- Затем ТЖ на время выполнения операции: DBMSSQL (+SDBL) с фильтром по базе, обязательно Duration; сумма длительностей
  запросов сравнивается со временем операции. Если запросы — малая доля, искать в коде (замер производительности),
  ожиданиях на блокировках, клиент-серверных вызовах (`i8105808`).
- Практические детали: платформа перечитывает logcfg.xml раз в минуту — после копирования ждать минуту и проверять,
  что журнал пишется; фильтр по базе (`p:processName`) ставить всегда; `<plansql/>` только узко и не на Oracle.

### 1.2. Долгие запросы (DBMSSQL/SDBL)
- Доля СУБД в серверном времени: сумма Duration DBMSSQL (или DBPOSTGRS) к сумме Duration CALL. Больше ~50% — повод
  разбирать запросы, меньше — искать в коде сервера (`…/troubleshooting/i8106011.htm`, пример на PostgreSQL,
  но приём общий).
- Группировка: суммарная длительность DBMSSQL/SDBL по последней строке контекста (модуль и строка кода), по Descr для
  EXCP, суммарное ожидание TLOCK (скрипты в `…/methods/i8105809.htm`).
- Высокий CPU SQL Server (`…/troubleshooting/i8105861.htm`): два подхода. (а) Со стороны СУБД — топ запросов кэша
  планов по CPU и по числу выполнений, индексы с высокими издержками, статистика ожиданий; (б) ТЖ DBMSSQL с
  большим числом чтений/длительностью, связь с контекстом 1С.
- Высокий CPU при «размазанной» нагрузке (`…/troubleshooting/i8105910.htm`, часть 2): много мелких запросов от больших
  пакетов. Методика — синхронно серверная трассировка SQL (Duration, CPU, Reads, Writes; 15–20 мин) и ТЖ DBMSSQL по
  базе без планов; оба набора нормализуются (убрать имена временных таблиц, параметры, пробелы), от нормализованного
  текста считается MD5, группировка по хэшу, затем объединение с контекстом ТЖ. Это ровно наш ШаблонХеш; у нас нет
  второй половины — CPU/Reads/Writes со стороны SQL.

### 1.3. CALL/SCALL, память и рабочие процессы
- Статьи раздела scalability не дают отдельной методики по свойствам CALL. По справке платформы (Руководство
  администратора 8.3.27, Приложение 3, `its.1c.ru/db/v8327doc/bookmark/adm/TI000000365`) у CALL/SCALL есть CpuTime,
  Memory, MemoryPeak, InBytes, OutBytes — это главный источник ответа «какой серверный вызов съел процессор/память».
- Высокий CPU на сервере приложений (`…/troubleshooting/i8105814.htm`): Processor Time ≈ 100%. Найти процесс
  (rphost/rmngr), в консоли кластера сравнить «Время вызовов (текущее)» и «Время СУБД (текущее)» по сеансам; если
  виноват служебный процесс — дамп ProcDump и обращение в 1С.
- Нехватка памяти (`…/troubleshooting/i8105815.htm`): Memory\Available MBytes мало. RamMap → какой процесс; для rphost —
  консоль кластера, сортировка сеансов по «Память (текущая)», затем код.
- Утечки памяти (`…/troubleshooting/i8105859.htm`): циклические ссылки в коде; расследование — отдельный лог CALL +
  LEAKS с `<leaks collect="1"><point call="server"/></leaks>`, history 12, только на время расследования (объёмный).
- Проблемы сетевого стека сервера (`…/troubleshooting/i8105857.htm`, ошибка «system lacked sufficient buffer space»)
  — исчерпание портов/буферов Windows; признак — массовые разрывы клиентов при живом сервере.

### 1.4. Счётчики ОС и кластера
- Минимальный набор Performance Monitor для продуктива (`i8105809`), шаг 5 с: Memory Available MBytes и Pages/sec,
  Processor(_Total) % Processor Time, System Processor Queue Length, % Processor Time и Private/Virtual Bytes процессов
  1cv8*, ragent, rmngr, rphost, LogicalDisk Free Megabytes, PhysicalDisk Avg. Disk Queue Length, Avg. Disk Bytes/Read
  и /Write. Сборщик — `logman create counter` в кольцевой файл + задача планировщика на автозапуск после перезагрузки.
- Диск SQL (`…/troubleshooting/i8105813.htm`): тревога при Avg. Disk sec/Read или sec/Write стабильно выше нормы
  (в статье порог записан как «> 2000» в единицах счётчика PerfMon); затем Resource Monitor — какие файлы, SSMS —
  какие запросы читают больше всех.
- Для расчёта оборудования (`…/methods/i8105810.htm`): средняя загрузка CPU, загрузка диска = 100 − % Idle Time,
  Cache Hit Ratio СУБД (ниже 80% — нехватка памяти), Memory Available.
- ЦКК (`i8105809`): контроль подключений (доступность ИБ), контроль памяти рабочих процессов с порогом и
  оповещением, разбор и архив дампов, оповещения по числу сеансов и любому счётчику с порогом.

## 2. События и свойства ТЖ: постоянный мониторинг и расследование

Постоянно на продуктиве (`…/methods/i8105809.htm`):
| Лог | Что | history | Назначение |
|---|---|---|---|
| All (минимальный) | EXCP и аварийные события процессов, `<dump>` | 28 ч | ~80% проблем платформы, падения rphost |
| LongEvents | все события с Durationus ≥ 20 000 000 (20 с) | 28 ч | длинные CALL/SCALL/запросы/Commit, «скромный» объём |
| TLOCKS | TLOCK/TTIMEOUT/TDEADLOCK | 4 ч | блокировки (разобрано ранее) |
| DBMSSQL | DBMSSQL по базе, `<plansql/>` узко | 4 ч | долгие запросы |
| 1cv8 (клиент) | полный на клиенте | 4 ч | только при расследовании клиента |

- В каталоге ТЖ не должно быть посторонних файлов — иначе запись молча прекращается (у нас уже в плане п.8).
- Для расследования — отдельные, узкие и короткие логи: DBMSSQL+планы на одну базу (history 2–48 ч, `i8105808`,
  `i8105861`), CALL+LEAKS (`i8105859`), всё подряд «all_mini» на несколько часов для доли СУБД/CALL (`i8106011`).
- Свойства: всегда Duration (лучше Durationus), контекст (Context), p:processName, Usr, t:connectID, SessionID;
  для запросов — Sql/Sdbl, Rows/RowsAffected, planSQLText при необходимости; для CALL — CpuTime, Memory, MemoryPeak,
  InBytes, OutBytes (справка платформы).
- Объём: длинные события и EXCP держать 28 ч и больше, подробные логи — часы; архивировать/выносить старые файлы.

## 3. Типовые причины и признаки

| Причина | Признак по ИТС | Источник |
|---|---|---|
| Неоптимальный план, сканирование | большие Reads у шаблона, индексы с высокими издержками, высокий CPU SQL | `i8105861` |
| Большие пакетные запросы | высокий CPU при отсутствии явного «тяжёлого» запроса; помогает только нормализация + MD5 | `i8105910` |
| Параллелизм | ожидания CXPACKET при MAXDOP = 0; ошибки «Intra-query parallelism…» / «deadlocked on thread communication buffer» → MAXDOP 1 | `…/troubleshooting/i8106008.htm`, `…/troubleshooting/i8105834.htm` |
| Медленный диск | PAGEIOLATCH_* длительно, WRITELOG/LOGBUFFER (журнал транзакций), IO_COMPLETION; Avg. Disk sec/Read/Write | `i8106008`, `i8105813` |
| Нехватка памяти под запрос | RESOURCE_SEMAPHORE (Hash/Sort), Cache Hit Ratio < 80% | `i8106008`, `i8105810` |
| Медленное приложение/сеть | ASYNC_NETWORK_IO — SQL отдал, rphost медленно забирает | `i8106008` |
| Нехватка CPU в SQL | высокая доля signal wait (ожидание планировщика) в dm_os_wait_stats | `i8106008` |
| Утечки памяти rphost | рост Private Bytes / памяти процесса, циклические ссылки | `i8105859`, `i8105815` |
| Неверный замер APDEX | два пика в распределении | `i8105808` |
| Соединения с виртуальными таблицами и подзапросами, ИЛИ, точка от составного типа | неоптимальный план, скан; лечится выносом во временную таблицу и параметрами ВТ | `…/standards/i8105842.htm` |
| Длительная транзакция, рост tempdb | падает свободное место tempdb, старые записи в dm_tran_active_snapshot_database_transactions | `…/troubleshooting/i8105900.htm` |
| Устаревшая статистика | планы деградируют; обновлять статистики не реже раза в сутки + чистка процедурного кэша | `…/administration/scenarios/i8105837.htm` |
| Динамическое обновление | отдельной статьи в разделе нет (проверено по оглавлению) | — |

Статистика ожиданий ИТС считает главным инструментом для SQL Server: топ dm_os_wait_stats без служебных ожиданий,
доля signal/resource wait (`i8106008`). Список служебных ожиданий для исключения в статье есть.

## 4. Чего у нас нет и что добавить

1. **Свойства CALL/SCALL** (CpuTime, Memory, MemoryPeak, InBytes, OutBytes) — добавить реквизиты в рбфВыполненияТЖ,
   разбор в СвойстваСобытияТЖ, в logcfg для CALL — `<property name="all"/>` или явный список. В «Запросах» (или
   новой форме «Вызовы») — топ контекстов по CPU и памяти. Это прямой ответ на «кто грузит rphost».
2. **Доля СУБД в серверном времени** — в почасовых агрегатах уже есть суммы по событиям; вывести отношение
   Σ DBMSSQL / Σ CALL по базе и часу, тревога при > 50% устойчиво.
3. **Лог длинных событий 20 с** (план п.5) и **минимальный прод-журнал EXCP + dump** (п.6) — по ИТС это база,
   брать их в первую очередь.
4. **Счётчики PerfMon из списка ИТС** — этап Б уже запланирован; сверить состав: добавить Processor Queue Length,
   Pages/sec, Avg. Disk sec/Read/Write, Private Bytes rphost; пороги тревог (память rphost, Available MBytes, диск).
5. **Статистика ожиданий SQL** — снимок dm_os_wait_stats раз в 5–15 мин с дельтой, без служебных ожиданий,
   доля signal wait (план п.10). Плюс топ dm_exec_query_stats по CPU/Reads с нормализацией в тот же ШаблонХеш —
   связка «SQL-сторона ↔ контекст 1С», как в `i8105910`.
6. **APDEX** (план п.11) — если в продуктивных базах подключена БСП «Оценка производительности», читать
   ЗамерыВремени и считать APDEX по ключевым операциям; иначе — не делать.
7. **Контроль памяти rphost и сеансов** по примеру ЦКК — порог памяти процесса, топ сеансов по «Память (текущая)»
   из rac session list (этап В уже снимает сеансы).
8. **Режим расследования** — кнопка «включить на N минут» для узких логов (DBMSSQL+plansql по базе/шаблону, CALL+LEAKS)
   с автоматическим откатом logcfg (план п.12 частично).

## 5. v8.1c.ru: технологии крупных внедрений

Источник: `https://v8.1c.ru/tekhnologii/tekhnologii-krupnykh-vnedreniy/` и вложенные страницы
(`…/korporativnyy-instrumentalnyy-paket/tsentr-upravleniya-proizvoditelnostyu/`, `…/tsentr-kontrolya-kachestva/`,
`…/test-tsentr/`, `…/standartnyy-nagruzochnyy-test/`, `…/tsentr-administrirovaniya/`,
`…/tsentry-korporativnoy-tekhnologicheskoy-podderzhki-tsktp/metodicheskie-materialy-po-tekhnologicheskim-voprosam-krupnykh-vnedreniy/`
(ссылки на разделы ИТС, разобранные выше), `…/vypolnennye-proekty-tsktp/oborudovanie-na-realnykh-vnedreniyakh/`).
Страницы описательные; сами продукты входят в КИП (платный пакет).

- **ЦУП** (Центр управления производительностью) — отдельная ИБ, подключается к кластеру, собирает ТЖ и показатели:
  интегральная оценка (APDEX), история производительности, поиск «узких мест» с полным контекстом на всех уровнях,
  **автоматическое ранжирование узких мест по влиянию** на общую производительность, регламентный мониторинг с
  реакцией на изменения, конструктор сценариев. Ближе всего к нашему base_list-мониторингу. Применимо: идея
  ранжирования (вес = Σ длительности по контексту/шаблону за период, а не просто топ по максимуму) и сравнение
  «до/после изменения» (метка выпуска конфигурации на графике шаблона). (По памяти проекта, ЦУП держим только как
  образец, функционал переносим в base_list.)
- **ЦКК** (Центр контроля качества) — регламентные и контрольные процедуры: доступность ИБ, память рабочих процессов,
  дампы, счётчики с порогами и оповещениями, ответственные и задачи. Применимо: модель «контрольная процедура →
  порог → оповещение → задача» у нас есть частично (тревоги в Telegram, правила реестра); стоит добавить контроль
  доступности ИБ (пробное подключение) и памяти rphost.
- **Тест-центр** и **Стандартный нагрузочный тест** — нагрузочные испытания и подбор оборудования. К постоянному
  мониторингу не относятся; не применимо, кроме приёма «сравнивать показатели версии с предыдущей».
- **Центр администрирования** — автоматизация обновлений и эксплуатации контура (скрипты Python, сценарии). Пересекается
  с нашими регл. заданиями обслуживания, но к производительности не относится; не применимо.
- **Оборудование на реальных внедрениях** — справочные конфигурации серверов (выделенный сервер мониторинга ЦКК
  на крупных системах). Для нас вывод: сбор ТЖ в той же ИБ base_list на S2019 допустим при наших объёмах, но
  лимит за запуск и чистку регистра нужно держать.

## 7. Дочитка ИТС с авторизацией (22.10.2026)

Читал в Chrome пользователя с входом на ИТС. Оглавление: `https://its.1c.ru/db/metod8dev/browse/13/-1/3199/3258`,
подразделы «Методики» (3267), «Администрирование» (3259, внутри MS SQL Server 3264, PostgreSQL, Linux…),
«Проблемы и решения» (3269), «Инструкции» (3266), «Стандарты разработки» (3268), «Разбор инцидентов ЦКТП» (3265).
Статья открывается как `https://its.1c.ru/db/metod8dev/content/<номер>/hdoc` (номер = хвост `i810NNNN`). Блокировки
повторно не разбирал.

Новые статьи, которых не было в переборе:

- **Перечень данных для расследования** (`content/6005/hdoc`, `…/instructions/i8106005.htm`) — главное новое. По типу
  проблемы готовые наборы logcfg (history 24, `<property name="all"/>`, EXCP всегда):
  высокий CPU сервера 1С → **CALL с фильтром `CpuTime > 0`** + счётчики + список сеансов; диск сервера 1С → CALL+SCALL;
  конкретный запрос → SDBL + DBMSSQL (DBPOSTGRS); плюс отдельные наборы на деградацию у части/всех пользователей,
  рост базы, рост сеансовых данных, реструктуризацию, закрытие месяца, дедлоки/таймауты, CPU/диск SQL. Это и есть
  «рекомендуемые настройки ТЖ», но под расследование, а не постоянные; постоянные — по-прежнему `i8105809`.
- **Top 25 вызовов по суммарной длительности** (`content/5906/hdoc`, `…/administration/scenarios/i8105906.htm`) —
  CALL с `property all`, history 12, группировка по последней строке Context, сумма/среднее/число. Подтверждает пункт 1
  раздела 4: CALL с контекстом и суммой — штатный приём ИТС.
- **Длительная транзакция и рост tempdb** (`content/5900/hdoc`, `…/troubleshooting/i8105900.htm`): свободное место
  tempdb из `sys.dm_db_file_space_usage` (unallocated_extent_page_count), затем самая старая транзакция из
  `sys.dm_tran_active_snapshot_database_transactions` (session_id, elapsed_time_seconds; актуально при RCSI, т.е. для
  8.3), по spid найти сеанс 1С, ЖР и узкий ТЖ по SessionID, исправлять код без перезапуска кластера. Транзакции в
  десятки–тысячи секунд ИТС считает дефектом. Для нас: метрика «свободно в tempdb» и «самая длинная snapshot-транзакция»
  в снимок SQL этапа Б/В — дёшево и полезно.
- **Стандарт «Типичные причины неоптимальной работы запросов»** (`content/5842/hdoc`, `…/standards/i8105842.htm`):
  соединения с подзапросами и с **виртуальными таблицами** (ВТ транслируется в подзапрос → плохой план; выносить во
  временную таблицу), несоответствие индексов условиям, ИЛИ в ГДЕ и в соединениях, подзапросы в условии соединения,
  точка от составного типа, фильтрация ВТ без параметров. Это чек-лист для разбора топ-шаблонов в «Запросах»; можно
  подсвечивать в тексте SDBL признаки (`ИЛИ` в `ПО`, `.Остатки(` в соединении без параметров).
- **Регламент СУБД MS SQL** (`content/5837/hdoc`, `…/administration/scenarios/i8105837.htm`): обновление статистик
  не реже раза в сутки, после него `DBCC FREEPROCCACHE`, дефрагментация индексов. Статья старая (SQL 2005), но
  требование «статистика ежедневно» — проверяемый пункт для мониторинга: дата последнего обновления статистик по
  крупным таблицам (`STATS_DATE`) с тревогой > 1–2 суток. Наш регламент индексов v3 — сверить, что статистику он обновляет.
- **Флаги трассировки SQL** (`content/5946/hdoc`): рекомендуемые глобально 610, 1117, 1118, 1211, 1224, 2330, 2371,
  4199, 8048 (многие не нужны на новых версиях SQL — в статье это оговорено). Для мониторинга: проверка `DBCC TRACESTATUS`
  против списка как разовый аудит настроек. Плюс `content/5904` (чек-лист настроек SQL), `content/5945` (MAXDOP).
- **Методика расследования проблем производительности** (`content/5902/hdoc`): классификация резкая/плавная деградация;
  при резкой — найти точный момент и сопоставить с изменениями (оборудование, конфигурация, настройки); при плавной —
  рост данных, дефицит CPU/диска/сети. Подтверждает идею метки выпуска конфигурации на графике шаблона.
- **Медленные операции с управляемой формой** (`content/5983/hdoc`): причина в примере — сериализация больших
  коллекций при клиент-серверных вызовах; меряется ТЖ на клиенте и сервере, InBytes/OutBytes CALL. Ещё довод хранить
  InBytes/OutBytes.
- **Память процессов** (`content/5985/hdoc`): порог внимания — процесс > ~20 ГБ без объяснимой операции, дамп и pid в
  поддержку. **Сеансовые данные** (`content/5860/hdoc`): хранятся в `srvinfo\reg_<порт>\snccntx*`, ими управляет
  rmngr, следить за свободным местом на этом диске и ростом каталога. `content/5954` — TCMalloc для Linux
  (динамическая память, не динамическое обновление).
- **Не найдено**: отдельной статьи про динамическое обновление конфигурации и про постоянные «рекомендуемые настройки ТЖ
  для продуктива» сверх `i8105809` в разделе нет. Остальные статьи раздела (веб-публикации, Сервер взаимодействия,
  1С:Шина, лицензирование, DB2/Oracle) к мониторингу не относятся.
