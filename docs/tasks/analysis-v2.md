# Задание: раздел «Анализ» v2 — детальные данные, как в 1С-Мониторе

Ветка `analysis-v2` от main, один PR, по-русски. Предыдущий PR #1/#2 уже в базе.

## Что не так сейчас (замечания пользователя после проверки в клиенте 20.10.2026)
1. «Запросы»: в колонке «Контекст / Запрос» непонятный текст — служебный SQL платформы (`{call sp_executesql(N'SELECT FileName,Creation,... FROM Config ...` , `SELECT CurrentSchema ... FROM SchemaStorage`), либо одна последняя строка стека. Нужен понятный 1С-текст, по которому можно найти событие в журнале регистрации и понять, что делал пользователь.
2. «Блокировки»: нет виновника — кто держал блокировку, его запрос и контекст, кого блокировал, сколько ждали.
3. «График» не работает вообще (проверь по коду: команда/форма открывается, но диаграмма не строится — найди причину).
Корень: источник — почасовые агрегаты `рбфСобытияТЖ` (агент берёт последнюю строку Context или первые 200 символов Sql). Для анализа как у Монитора нужны отдельные события.

## Что сделать
1. Регистр `рбфВыполненияТЖ` (непериодический, независимый, измерения: Ид события String(36)) с реквизитами: Время (окончание события, с мс), Сервер, База, Событие (DBMSSQL/SDBL/CALL/TLOCK/TTIMEOUT/TDEADLOCK/EXCP), ДлительностьМс, Пользователь (Usr), СеансИд (SessionID), СоединениеИд (t:connectID), КлиентИд (t:clientID), Приложение (t:applicationName), Компьютер (t:computerName), dbpid, Транзакция (trans), Строк (Rows/RowsAffected), КонтекстПолный (весь стек Context, строка неогр.), КонтекстТочка (первая строка стека — точка входа: форма/команда), КонтекстСтрока (последняя строка — где выполнялось), ТекстЗапроса1С (свойство Sdbl события SDBL — запрос в терминах 1С; для DBMSSQL — Sql с заменой имён таблиц `_Reference139` → `Справочник.Имя` через `ПолучитьСтруктуруХраненияБазыДанных` по базе, кэшировать карту в регистре), ТекстSQL, ШаблонХеш (MD5 нормализованного шаблона: литералы и параметры @P → ?), Пространства/Locks (TLOCK), ЖдалСоединения (WaitConnections), Виновник* (см. п.3), Исключение/Описание (EXCP). Глубина хранения — настройка (по умолчанию 14 дней) + регламентная очистка.
2. HTTP `rbf-admin` POST `tj-events` {server, events:[...]} — пакетная запись (до 5000 за вызов, идемпотентно по Ид = хеш файл+смещение). Источник — tj-analyzer (этап 8, команда export-events) или агент; описать JSON в `docs/tj-events-schema.md`.
3. Блокировки: для TLOCK/TTIMEOUT с непустым WaitConnections найти «виновника»: последнее событие соединения из WaitConnections до времени ожидания (TLOCK/SDBL/DBMSSQL того же СоединениеИд в той же транзакции) → Виновник: пользователь, сеанс, контекст, запрос 1С, начало транзакции. Форма «Блокировки» как у Монитора: слева группы по пространству блокировок (Регистр/Справочник по карте имён) с количеством и суммарным ожиданием, справа список ожиданий (время, ждал сек, пострадавший пользователь/контекст), внизу две колонки «Жертва» и «Виновник» (пользователь, сеанс, контекст точка+строка, запрос 1С, транзакция), страница «Схема». TDEADLOCK — по DeadlockConnectionIntersections, обе стороны.
4. «Запросы»: группировка по ШаблонХеш с показом КонтекстТочка + ТекстЗапроса1С (не SQL), отфильтровать служебные запросы платформы (Config, Params, SchemaStorage, DBSchema, _YearOffset, sp_reset_connection и т.п. — список в настройке). Справа выполнения с пользователем, сеансом, временем; страницы внизу: «Контекст» (полный стек), «Запрос 1С», «SQL», «Сведения» (сеанс, соединение, клиент, приложение, компьютер, dbpid, строк), кнопка **«Найти в журнале регистрации»** — открыть ЖР нужной базы (или выборку ВыгрузитьЖурналРегистрации нет — у нас разные базы) с отбором по пользователю, номеру сеанса и интервалу ±1 мин от Времени; если база не base_list — показать готовые параметры отбора (Сеанс, Пользователь, интервал) для копирования.
5. «График»: починить; показатели из рбфСчетчики и количества/длительности рбфВыполненияТЖ по минутам/часам; таблица показателей с флажками, ось, масштаб; клик по точке — расшифровка (выполнения за интервал).
6. Настройка ТЖ (форма из PR #2): убедиться, что генерируемый logcfg содержит то, что нужно для пп.1–3: SDBL с Sdbl (по базе, длительность ≥ порога), DBMSSQL со всеми нужными свойствами (Context, Usr, SessionID, t:connectID, t:clientID, dbpid, trans, Rows, Sql), TLOCK/TTIMEOUT без порога со свойствами Locks, WaitConnections, Context, Usr, SessionID, SDBL Commit/Rollback, TDEADLOCK с DeadlockConnectionIntersections. Эталон — `monitor-logcfg-ref.md`. Свойство SessionID добавить везде (по нему — связь с ЖР).
