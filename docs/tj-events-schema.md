# rbf-admin/tj-events и tj-storage: детальные события ТЖ для раздела «Анализ»

Раздел «Анализ» (формы «Запросы», «Блокировки», «График») строится по отдельным событиям ТЖ
из регистра `рбфВыполненияТЖ`. Сам base_list ТЖ не читает: события присылает **tj-analyzer**
(этап 8, команда `export-events`) или агент rbf. Почасовые агрегаты `rbf-admin/techlog`
(`рбфСобытияТЖ`) остаются для отчёта «Проблемы производительности (ТЖ)» и тревог.

Доступ: роль `рбфАгентМониторинга` (учётка агента), `рбфАдминAPI` или `ПолныеПрава`.
Тело запроса — JSON в UTF-8.

## POST /hs/rbf-admin/tj-events

```json
{
  "server": "MSK-1C8-APP01",
  "events": [
    {
      "id": "3f2a9c...e1",
      "time": "2026-10-20T10:15:03.123456",
      "duration_us": 5234000,
      "base": "trade",
      "event": "SDBL",
      "usr": "Иванов И.И.",
      "session": 1834,
      "connect": 27712,
      "client": 1290,
      "app": "1CV8C",
      "computer": "PC-SALES-07",
      "dbpid": 77,
      "trans": "1",
      "rows": 120,
      "rows_affected": 0,
      "func": "",
      "context": "Документ.Заказ.Форма.ФормаДокумента.Форма : 512 : Записать();\nОбщийМодуль.Склад.Модуль : 88 : Запрос.Выполнить();",
      "sdbl": "SELECT T1.Ref FROM Document.Заказ T1 WHERE ...",
      "sql": "",
      "locks": "",
      "wait_connections": "",
      "deadlock": "",
      "exception": "",
      "descr": "",
      "template_hash": ""
    }
  ]
}
```

| Поле | Обязательное | Свойство ТЖ | Куда пишется |
|---|---|---|---|
| `server` | да | — | `Сервер` (имя сервера 1С, как в `metrics`/`techlog`) |
| `events` | да | — | массив, не больше **5000** событий за вызов |
| `id` | желательно | — | `Ид` (до 36 символов). **Хеш «путь к файлу + смещение строки»**: по нему повторная отправка пропускается. Нет `id` — base_list считает MD5 от сервера, времени, события, соединения и длительности |
| `time` | да | время в имени файла + `mm:ss.ffffff` | `Время` (секунды) и `Момент` (мкс от 01.01.2000). Окончание события, **местное время сервера 1С**, формат `ГГГГ-ММ-ДДTчч:мм:сс[.ffffff]` |
| `duration_us` | да | `duration` (8.3.12+, мкс) | `ДлительностьМс`; вместо него можно прислать `duration_ms` |
| `base` | да | `p:processName` | `База` |
| `event` | да | имя события | `Событие`: DBMSSQL, DBPOSTGRS, SDBL, CALL, TLOCK, TTIMEOUT, TDEADLOCK, EXCP, QERR |
| `usr` | | `Usr` | `Пользователь` |
| `session` | | `SessionID` | `СеансИд` — номер сеанса, колонка «Сеанс» журнала регистрации |
| `connect` | | `t:connectID` | `СоединениеИд` — по нему ищется виновник блокировки |
| `client` | | `t:clientID` | `КлиентИд` |
| `app` | | `t:applicationName` | `Приложение` |
| `computer` | | `t:computerName` | `Компьютер` |
| `dbpid` | | `dbpid` | `ПроцессСУБД` |
| `trans` | | `trans` | `Транзакция` |
| `rows`, `rows_affected` | | `Rows`, `RowsAffected` | `Строк` (большее из двух) |
| `func` | | `Func` (SDBL) | `ФункцияSDBL`. По `CommitTransaction` / `RollbackTransaction` определяется начало транзакции виновника |
| `context` | | `Context` | `КонтекстПолный` — весь стек; первая непустая строка — `КонтекстТочка` (точка входа: форма, команда), последняя — `КонтекстСтрока` (где выполнялось) |
| `sdbl` | | `Sdbl` (SDBL) | `ТекстЗапроса1С` — запрос на языке 1С |
| `sql` | | `Sql` | `ТекстSQL`; для DBMSSQL `ТекстЗапроса1С` получается заменой `_Reference139` → `Справочник.Имя` по карте имён (см. tj-storage) |
| `locks` | | `Locks` (TLOCK, TTIMEOUT) | `Пространства`; первое пространство (`AccumRg123.DIMS`) — `Пространство` |
| `wait_connections` | | `WaitConnections` | `ЖдалСоединения` — кого ждали; непустое значение означает ожидание, и тогда ищется виновник |
| `deadlock` | | `DeadlockConnectionIntersections` | `ПересеченияВзаимоблокировки` |
| `exception`, `descr` | | `Exception`, `Descr` (EXCP) | `Исключение`, `Описание` |
| `template_hash` | | — | `ШаблонХеш`: MD5 нормализованного текста запроса. Если не прислан, base_list считает его сам по первым 1500 символам: литералы, числа и `@P1` → `?`, пробелы схлопываются, хвост `p_0: ...` отбрасывается. Отправителю выгоднее считать хеш у себя — так быстрее |

Числа можно присылать числом или строкой. Пустые и отсутствующие поля равнозначны.

**Что не пропустит base_list:**
- больше 5000 событий в пакете — ответ 400;
- событие без `time` или со временем не в формате ISO — ответ 400 на весь пакет.

**Ответ 200:**

```json
{"received": 5000, "written": 4987, "duplicates": 13, "culprits": 42}
```

- `duplicates` — события, которые уже были записаны (тот же `id`), или повторы внутри пакета;
- `culprits` — для скольких ожиданий на блокировке (TLOCK/TTIMEOUT с `wait_connections`) найден виновник.

**Как ищется виновник.** Берётся последнее событие соединения из `wait_connections` до окончания ожидания, кроме Commit/Rollback, не раньше чем за час. Начало транзакции виновника — его первое событие после предыдущего Commit/Rollback. Если события виновника приходят позже ожидания, виновник находится при открытии ожидания в форме «Блокировки».

**Служебные запросы платформы** при записи помечаются `Служебный = Истина`; форма «Запросы» их скрывает. Помечается запрос, в котором есть отдельное слово из настройки `ТЖСлужебныеЗапросы` в `НастройкиПравилРеестра`. По умолчанию: `Config, ConfigSave, Params, Files, SchemaStorage, DBSchema, IBVersion, _YearOffset, sp_reset_connection, _SystemSettings, _CommonSettings, _RepSettings, _FrmDtSettings, _UsersWorkHistory`.

**Глубина хранения:**
- настройка `ХранитьВыполненияТЖДней`, по умолчанию 14;
- очистка идёт в суточном цикле `ИтогиМониторинга`, не больше `ОчисткаВыполненийТЖЗаПроход` записей за проход (по умолчанию 100 000).

## POST /hs/rbf-admin/tj-storage

Карта имён таблиц СУБД базы → имена метаданных. Нужна, чтобы:
- SQL событий DBMSSQL показывался «в терминах 1С»;
- пространства блокировок назывались `РегистрНакопления.ТоварыНаСкладах (DIMS)`, а не `AccumRg123.DIMS`.

Карта базы заменяется целиком.

```json
{
  "base": "trade",
  "tables": [
    {"storage": "_Reference139", "name": "Справочник.Контрагенты"},
    {"storage": "_AccumRg12345", "name": "РегистрНакопления.ТоварыНаСкладах"},
    {"storage": "_Document512_VT513", "name": "Документ.Заказ.Товары"}
  ]
}
```

Ответ: `{"written": 3}`.

Для базы, в которой работает сам base_list, карта заполняется автоматически:
- в суточном цикле;
- командой очереди `ОбновитьИменаТаблиц` (`rbf-admin/enqueue {"command":"ОбновитьИменаТаблиц"}`).

Для других баз `ПолучитьСтруктуруХраненияБазыДанных` нужно выполнить в самой базе. Например, внешней обработкой или через `1cv8 /Execute` на исполнителе, а результат отправить в tj-storage:

```bsl
Структура = ПолучитьСтруктуруХраненияБазыДанных(, Истина); // Истина - имена таблиц СУБД (_Reference139)
Таблицы = Новый Массив;
Для Каждого Строка Из Структура Цикл
	Если ЗначениеЗаполнено(Строка.ИмяТаблицы) Тогда
		Таблицы.Добавить(Новый Структура("storage,name", Строка.ИмяТаблицыХранения, Строка.ИмяТаблицы));
	КонецЕсли;
КонецЦикла;
// POST /hs/rbf-admin/tj-storage {"base": "<имя базы в кластере>", "tables": Таблицы}
```

## Что должно быть в logcfg

logcfg формирует форма «Настройка ТЖ» → `ПравилаРеестраБаз.СформироватьLogcfg`.

| Нужно для | Показатель | События и свойства |
|---|---|---|
| «Запросы» | долгий запрос | DBMSSQL и SDBL с длительностью от порога; свойства `Context`, `Usr`, `SessionID`, `t:connectID`, `t:clientID`, `t:applicationName`, `t:computerName`, `dbpid`, `trans`, `Rows`, `RowsAffected`, `Sql`, `Sdbl`, `Func` |
| «Блокировки» | ожидание на блокировке | TLOCK и TTIMEOUT **без порога** с `Locks`, `WaitConnections`, `Context`, `Usr`, `SessionID`, `t:connectID`, `trans` |
| Начало транзакции виновника | транзакции | SDBL с Func = CommitTransaction / RollbackTransaction |
| «Взаимоблокировки» | взаимоблокировка | TDEADLOCK с `DeadlockConnectionIntersections` |

`SessionID` пишется во всех логах: по нему событие ТЖ связывается с сеансом в журнале регистрации (кнопка «Найти в журнале регистрации» в форме «Запросы»).
