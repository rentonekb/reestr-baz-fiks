# Отдельные события ТЖ: регистр рбфВыполненияТЖ и метод tj-events

Контракт между агентом (`C:\claude\knowledge\baselist\agent\rbf_agent.ps1`) и расширением РеестрБазФикс.
Почасовые агрегаты `рбфСобытияТЖ` остаются как есть: «Ошибки ТЖ» и сводка работают на них.

## Регистр сведений рбфВыполненияТЖ

Непериодический, независимый, запись — по одному событию. Глубина хранения задаётся `рбфНастройкиТЖ`
(параметр «ГлубинаВыполненийДней», по умолчанию 14), очищает регламентное задание `рбфОчисткаВыполненийТЖ` раз в сутки.

| Поле | Вид | Тип | JSON | Откуда в ТЖ |

1С обрезает значения до длины реквизита.

## POST rbf-admin/tj-events

Учётка агента `РЗ_АгентМониторинга`, роль `рбфАгентМониторинга` (добавить право на регистр).

```json
{ "server": "S2019",
  "events": [ { "id": "9f1c...", "time": "2026-10-20T14:05:31", "us": 123456, "event": "TLOCK", "ms": 2500.0,
                "db": "base_list", "usr": "Похожаев Илья", "session": 15, "connect": 482, "client": 1203,
                "app": "1CV8C", "computer": "rds", "pid": "4412", "dbpid": 77, "trans": true, "rows": 0, "func": "",
                "ctx": "Форма.Записать...\nОбщийМодуль.X.Модуль : 120 : ...", "sdbl": "", "sql": "",
                "locks": "AccumRg123.DIMS Exclusive Fld456=...", "wait": "482,519", "deadlock": "",
                "exception": "", "descr": "" } ] }
```

- Поля, которых у события нет, можно не передавать.
- До 5000 событий за вызов. Запись идемпотентна: повторный пакет с тем же `id` перезаписывает строку.
- Ответ: `{"ok": true, "written": N}` или HTTP 400 `{"ok": false, "error": "..."}`.
- Ошибка одного события (неверная дата) не отменяет пакет: событие пропускается и учитывается в `skipped`.

## Что считает 1С при записи

1. **ТекстЗапроса1С для DBMSSQL.** Если `sdbl` пустой: имена таблиц `_Reference139`, `_AccumRg123`, `_Fld456`
   в Sql заменяются на имена метаданных. Карта есть только для базы, где работает код (`ПолучитьСтруктуруХраненияБазыДанных`),
   то есть для base_list; она кэшируется в `рбфИменаТаблицТЖ` (База, ИмяХранения -> ИмяМетаданных). Для других баз
   поле остаётся пустым, форма показывает SQL. Для TLOCK поле Блокировки тоже переводится по карте при показе.
2. **ШаблонХеш.** MD5 от текста (Sdbl, иначе Sql), где строковые и числовые литералы, `@P1`, `p_0:...` и хвост параметров
   заменены на `?`, пробелы схлопнуты.
3. **ВиновникИд** для TLOCK/TTIMEOUT с непустым `wait`: для каждого соединения из ЖдалСоединения — TLOCK этого
   СоединениеИд (тот же сервер и база), взятый до начала ожидания, иначе последний SDBL/DBMSSQL (см. «Реализация»). Для TDEADLOCK обе стороны берутся при показе
   из DeadlockConnectionIntersections.
   Если виновник приходит в следующем пакете, он заполняется при следующем вызове (дозаполнение строк без ВиновникИд за час до самого раннего события пакета).

## logcfg и разбор (22.10.2026, пп.4–8 плана)

- Пороги — по `durationus` (мкс): порог настройки в секундах × 1 000 000 (было `duration` × 10 000).
- `LongEvents` (`<каталог>\<база>_<порт>\LongEvents`, history 28): все события с `durationus >= 20000000`
  по каждой базе с хотя бы одним включённым показателем. Из этого лога разбираются события любого имени.
- `Prod` (`<каталог>\Prod`, history 28, без фильтра по базе, `property all`): EXCP, CONN, PROC, ADMIN, SESN, CLSTR;
  `<dump>` не пишется (решение 22.10.2026), флаг ДампПроцесса в рбфНастройкиТЖ остался, но не используется.
  Суточного архива ТЖ нет: события грузятся в базу и чистятся регламентом.
  В регистр: PROC — все; CONN и CLSTR — только с Descr или Exception; ADMIN/SESN — только в файлах.
  Если Descr пустой, в Описание идёт свойство Txt.
- Новые имена событий в фильтре разбора: SCALL, CONN, PROC, CLSTR.
- DBMSSQL (Queries и SQL_Locks) пишет `lka,lkp,lkpid,lkaid,lksrc,lkpto,lkato`. Новых реквизитов нет:
  все lk* строкой `lkp=1 lkpid=… lksrc=…` → Блокировки (`locks`); ЖдалСоединения не заполняется (признак ожидания TLOCK).
  ВиновникИд: `рбфАнализСервер.ЗаполнитьВиновниковБлокировокСУБД` сначала вызывает `ЗаполнитьВиновниковПоLksrc` —
  последнее TLOCK/SDBL/DBMSSQL соединения lksrc (тот же сервер и база) в [начало ожидания − 10 мин; Время], кроме
  Commit/Rollback; затем, как раньше, SQLBLOCK из XE по БлокирующийSpid (запасной путь).
- Контроль ТЖ (`ПравилаРеестраБаз.КонтрольТЖ`, из СборТЖ): через 1–2 мин после выполненной команды ЗаписатьLogcfg —
  есть ли `*.log`, изменённые после записи, иначе Telegram; в :02 каждого часа — объём каталога и прирост за прошлый
  час (файлы `yyMMddHH.log`), пороги `ТЖТревогаЧасМб` (2048) и `ТЖТревогаКаталогГб` (100), итог в ЖР «Мониторинг.КонтрольТЖ».

## Реализация (рбфАнализСервер) и отклонения

- Метод шаблона URL не добавлялся: `rbf-admin/{method}` уже принимает POST, `tj-events` добавлен в список методов агента
  (право Use на метод `Команда.Выполнить` у роли `рбфАгентМониторинга` уже есть).
- Успешный ответ: `{"ok": true, "written": N, "skipped": M}`. Ошибка всего пакета (нет `server`, больше 5000 событий) —
  HTTP 400 в общем стиле сервиса `{"error": "..."}`, без поля `ok`.
- Пропускаются (skipped) события без `id` и с `time`, который не разбирается как `yyyy-MM-ddTHH:mm:ss`.
- Если агент не передал `ctxTop`/`ctxLast`, они берутся из `ctx` (первая и последняя непустые строки).
- ТекстЗапроса1С для DBMSSQL: текущая ИБ определяется по `Ref` из `СтрокаСоединенияИнформационнойБазы()`
  (сравнение с `db` без учёта регистра); из `{call sp_executesql(N'...')}` берётся внутренний текст.
  Поля переводятся в имя реквизита без таблицы (`T1._Fld456RRef` -> `T1.Реквизит`).
- Кэш карты: `ПолучитьСтруктуруХраненияБазыДанных(, Истина)` (имена как в СУБД), дата построения — запись
  `ИмяХранения = "*"`, `ИмяМетаданных` = XMLСтрока даты.
- ШаблонХеш — MD5 в нижнем регистре hex; литерал `N'...'` даёт `N?`.
- Дозаполнение виновника: кроме событий пакета, строки TLOCK/TTIMEOUT без ВиновникИд того же сервера
  со Временем не раньше (минимальное Время событий пакета − 1 ч).
- Окно виновника (методика ИТС i8106006): начало ожидания = Время − ДлительностьМс/1000 (с точностью до секунды).
  Для каждого соединения из ЖдалСоединения по порядку берутся его TLOCK в транзакции, которая шла в начале
  ожидания: после последнего SDBL CommitTransaction/RollbackTransaction соединения до начала ожидания, а без него —
  в [начало ожидания − 10 мин; начало ожидания]. Приоритет (везде самый поздний TLOCK): 0 — то же пространство,
  не обе Shared и совпадают значения всех общих полей Locks (поле, которого нет в записи, — весь диапазон);
  1 — то же пространство; 2 — любой TLOCK. Если TLOCK нет — последний SDBL/DBMSSQL соединения в той же транзакции
  до Время жертвы, кроме Commit/Rollback. Один запрос на пакет, выбор в коде (`ВиновникВТранзакции`).
- Карточка формы «Блокировки» показывает транзакцию виновника: события его соединения от прошлого Commit/Rollback
  по первый Commit/Rollback после начала ожидания и её длительность. Без показателя «Транзакции» (SDBL Commit)
  границы не известны: длительность помечается «не меньше», окно — 10 мин.

## Блокировки СУБД (SQLBLOCK, SQLDEADLOCK)

Источник — не ТЖ, а XE-сессия SQL Server `rbf_blocking` (`blocked_process_report` при
`blocked process threshold (s)` = 5 и `xml_deadlock_report`, файлы `rbf_blocking_*.xel` в каталоге Log SQL).
Читает регламентное задание рбфСборТЖ после файлов ТЖ (`ПравилаРеестраБаз.СобратьБлокировкиСУБД`).

- **Какие серверы.** SQL-серверы (`СерверыИБазы.СерверБД`, пусто — `localhost`), где хотя бы у одной базы реестра
  в `рбфНастройкиТЖ` включены `ОжиданиеНаБлокировкеСУБД` или `ВзаимоблокировкаСУБД`. Подключение — `sqlcmd`
  (`КомандаSQL`, учётка СУБД из файла), пакет: `sys.fn_xe_file_target_read_file(N'rbf_blocking*.xel', NULL, @file, @offset)`.
  Строка ответа: `file_name|file_offset|object_name|OBJECT_NAME(object_id, database_id)|event_data в base64 (UTF-16LE)`.
- **Позиция.** `рбфПозицииФайловТЖ`: Сервер = `sql:<сервер SQL>`, ПутьХеш = MD5("rbf_blocking"), Путь = file_name,
  Смещение = file_offset последнего прочитанного блока XE. Первый запуск — с начала файлов, события не старше 2 ч.
  Позиция не читается (файл ушёл ротацией) — чтение с начала с тем же фильтром 2 ч, повторы безопасны (Ид).
  Не больше min(остаток лимита запуска, 5000) событий; если упёрлись в предел, позиция ставится на предыдущий блок
  (события блока делят один file_offset), следующий запуск перечитает последний блок.
- **База.** `database_name` (для взаимоблокировки, если пусто, — `currentdbname` жертвы) переводится по
  `СерверыИБазы` (СерверБД + ИмяБазыБД → ИмяБазы1С), Сервер события — сервер 1С этой базы без порта (как у DBMSSQL).
  БД без строки реестра (tempdb, master, чужие) пишется как есть, Сервер — имя SQL-сервера. Если база в реестре есть,
  но показатель выключен — событие пропускается.
- **Время** — `event/@timestamp` (UTC) → `МестноеВремя(..., ЧасовойПояс())` сервера 1С.
- **SQLBLOCK**: Ид = MD5(`SQLBLOCK|сервер|БД|spid|xactid|waitresource` ждущего, нижний регистр) — повторные отчёты
  одного эпизода (каждые 5 с) дают одну строку: ДлительностьМс = максимальный waittime, Время — отчёт с ним.
  dbpid/Компьютер/Приложение/ТекстSQL/Транзакция — ждущего; БлокирующийSpid/ТекстSQLВиновника — блокирующего;
  Описание — строки `Ждущий: spid=..., loginname=..., ...` и `Блокирующий: ...`.
- **ВиновникИд** (SQLBLOCK): последнее DBMSSQL той же базы с dbpid = БлокирующийSpid и Временем в
  [начало ожидания − 10 мин; начало ожидания], начало ожидания = Время − ДлительностьМс/1000. Не найден — пусто,
  форма показывает данные блокирующего процесса SQL. Строки SQLBLOCK без виновника за последний час дозаполняются
  каждым запуском (`рбфАнализСервер.ЗаполнитьВиновниковБлокировокСУБД`).
- **SQLDEADLOCK**: Ид = MD5(`SQLDEADLOCK|сервер|timestamp|id жертвы`); Взаимоблокировка — XML события целиком,
  Описание — `Жертва: ...` и `Участник: ...` (с inputbuf); dbpid — жертвы, БлокирующийSpid — первого другого участника.
- **Форма** «Анализ блокировок», вид «СУБД»: группы по таблице из РесурсОжидания (для текущей ИБ — имя метаданных
  через `КартаИменТаблиц`), SQLBLOCK и SQLDEADLOCK вместе (в «Взаимоблокировки» не попадают: там разбор
  DeadlockConnectionIntersections ТЖ).

## GET rbf-admin/agent-config

Настройки агента мониторинга `rbf_agent` для сервера. Задаются на странице «Агенты» формы
«Настройки мониторинга» (раздел «Анализ»), хранятся в `НастройкиПравилРеестра`:
`Параметр = "Агент." + <сервер>`, `Значение` — компактный JSON (строка до 500 символов,
значения по умолчанию не пишутся). Доступ: `ПолныеПрава`, `рбфАдминAPI` или `рбфАгентМониторинга`.

Запрос: `GET /hs/rbf-admin/agent-config?server=S2019` (`server` — имя из `agent.json`).

Ответ, если настройки сервера записаны:

```json
{"server":"S2019","techlogDir":"D:\logs_1c\rbf","disks":["C","D"],"processes":["rphost","ragent","rmngr"],
 "sql":[{"name":"S2019","instance":"MSSQLSERVER"}],"skipEvents":["EXCPCNTX"],"topPerEvent":100,
 "sendEvents":true,"eventsBatch":2000,"maxText":20000}
```

Если настроек нет — только `{"server":"S2019","techlogDir":"..."}`; агент оставляет свои значения.

`techlogDir`: каталог из настроек агента; если пуст — `КаталогЛогов` строки сервера `рбфНастройкиТЖ`
(`Сервер1С` = сервер, `ИмяБазы1С` = ""), если и там пусто — настройка `КаталогЛоговТЖ`
(по умолчанию `D:\logs_1c\rbf`, как в `СформироватьLogcfg`).

Умолчания полей: `disks`, `processes`, `sql` — пустые списки, `skipEvents` — `["EXCPCNTX"]`,
`topPerEvent` 100, `sendEvents` true, `eventsBatch` 2000, `maxText` 20000.
Реализация: `ПравилаРеестраБаз.КонфигурацияАгента`.
